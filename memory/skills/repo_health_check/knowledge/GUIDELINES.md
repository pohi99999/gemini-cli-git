# Repository Health Check Skill

## Purpose

This skill monitors a target repository to check if all processes are working correctly and provides suggestions when problems are detected.

**Example use case**: Daily health checks for the mcp-brunella-core repository to proactively identify issues, broken builds, failing tests, outdated dependencies, or other problems.

## Skill Overview

This skill shows you how to:
- Clone and analyze a target repository
- Check build and test status
- Review GitHub Actions workflow runs
- Identify issues with dependencies
- Detect code quality problems
- Monitor for stale branches or PRs
- Provide actionable suggestions for problems found

## How to Execute This Skill

### 1. Repository Setup

Clone or update the target repository to analyze it:

```bash
# Define local clone location
REPO_DIR="/tmp/target-repo"
TARGET_REPO="mcp-brunella-core"  # Or from demand file

# Clone or update the repository
# First, search for the repository or use the configured owner
if [ -d "$REPO_DIR" ]; then
  cd "$REPO_DIR"
  git pull origin main
else
  # Note: You'll need to determine the correct owner/organization
  # You can search GitHub or use a configured value
  git clone "https://github.com/{owner}/$TARGET_REPO" "$REPO_DIR"
fi

cd "$REPO_DIR"
```

### 2. Health Check Areas

When analyzing repository health, check the following areas:

**Build Status:**
- Check if the project builds successfully
- Identify build errors or warnings
- Review build configuration files

**Test Status:**
- Run existing test suites
- Check test coverage
- Identify failing or flaky tests

**Dependencies:**
- Check for outdated dependencies
- Identify security vulnerabilities in dependencies
- Review dependency update needs

**Code Quality:**
- Check for linting errors
- Review code style consistency
- Identify potential bugs or anti-patterns

**GitHub Actions/CI:**
- Review recent workflow runs
- Check for failing workflows
- Identify workflows that haven't run recently

**Repository Health:**
- Check for stale branches
- Review open PRs that need attention
- Identify issues that need triage
- Check for outdated documentation

**Security:**
- Check for security vulnerabilities
- Review security advisories
- Check for exposed secrets or credentials

### 4. Problem Detection Strategy

To identify problems effectively:

**Automated Checks:**
1. Clone/update repository
2. Check if build system exists (package.json, Makefile, etc.)
3. Run build command if available
4. Run test command if available
5. Check for linting configuration and run linters
6. Check dependency files for outdated packages
7. Use GitHub API to check workflow status
8. Analyze git log for recent activity patterns

**Manual Analysis:**
1. Review recent commits for patterns
2. Check documentation currency
3. Review open issues and PRs
4. Check for common anti-patterns
5. Review security practices

**Prioritization:**
- Critical: Build failures, security vulnerabilities, production-blocking issues
- High: Test failures, dependency issues with known fixes
- Medium: Code quality issues, outdated dependencies without vulnerabilities
- Low: Documentation updates, minor improvements

### 5. Quality Standards

**Accuracy:**
- ✅ Verify all issues found are real problems
- ✅ Test suggested solutions when possible
- ✅ Link to relevant documentation and resources
- ✅ Provide context for each issue
- ✅ Check against latest repository state

**Clarity:**
- ✅ Use clear, actionable language
- ✅ Explain the impact of each issue
- ✅ Provide step-by-step solutions
- ❌ Don't use overly technical jargon without explanation

**Practicality:**
- ✅ Include working commands and examples
- ✅ Provide priority levels for issues
- ✅ Link to official documentation
- ✅ Show real-world impact
- ❌ Don't suggest theoretical solutions without validation

**Completeness:**
- ✅ Check all major health areas
- ✅ Provide summary and detailed findings
- ✅ Include metrics and trends
- ✅ Suggest preventive measures
- ❌ Don't skip areas even if they appear healthy

## Output Requirements

### File Naming
Use descriptive, timestamped filenames:
- Format: `YYYY-MM-DD-health-check.md`
- Example: `2025-11-22-health-check.md`

### Location
Save all reports to: `memory/skills/repo_health_check/output/`

### Metadata Tracking
Maintain a metadata file to track health history:
- File: `memory/skills/repo_health_check/output/health-history.json`
- Structure:
```json
{
  "checks": [
    {
      "date": "2025-11-22T22:00:00Z",
      "repository": "mcp-brunella-core",
      "status": "healthy|issues|critical",
      "issues_found": 3,
      "critical_issues": 0,
      "build_status": "pass",
      "test_status": "pass",
      "key_findings": ["Outdated dependencies", "Stale branch"]
    }
  ]
}
```

### Format
- Use Markdown format
- Include metadata (date, repository, status)
- Follow the structure template above
- Use status emojis for quick scanning (✅ ⚠️ ❌)
- Ensure code blocks have proper syntax highlighting
- Keep it readable and well-formatted

## When to Skip Execution

Skip health check if:
- Repository clone/update fails (network issues, access denied)
- Repository has been archived or deleted
- Previous check completed within last 6 hours (prevent duplicate runs)
- Repository is in maintenance mode (check README or status page)

## Example Workflow

1. **Clone/update repository** from GitHub
2. **Check build system** (package.json, requirements.txt, etc.)
3. **Run build** if build system exists
4. **Run tests** if test suite exists
5. **Check dependencies** for updates and vulnerabilities
6. **Query GitHub API** for workflow status
7. **Analyze results** and categorize by severity
8. **Generate report** using the template structure
9. **Update health history** with new entry
10. **Save to output directory** with proper filename
11. **Quality check** against standards above

## Tips for Success

- Start with automated checks before manual analysis
- Focus on actionable findings over theoretical issues
- Provide clear, step-by-step solutions
- Include links to relevant documentation
- Track trends over time using health history
- Prioritize security and build issues
- Be specific about impacts and risks
- Include commands that users can copy-paste
- Update health history for trend analysis

## Common Pitfalls to Avoid

- ❌ Reporting false positives (verify issues are real)
- ❌ Overwhelming with minor issues (prioritize)
- ❌ Vague suggestions (be specific and actionable)
- ❌ Not checking if suggested solutions work
- ❌ Ignoring context (consider repository purpose)
- ❌ Not linking to relevant resources
- ❌ Forgetting to update health history
- ❌ Running checks too frequently (respect rate limits)
